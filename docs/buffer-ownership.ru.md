# Чьи это байты

[English](buffer-ownership.md) · **Русский**

Самый частый способ испортить сетевой трафик в Node — самая соблазнительная оптимизация: *использовать один буфер на все пакеты*. В 2pack этот приём есть, он подписан, и рядом лежит более безопасный способ получить тот же результат без аллокаций. Здесь объясняется почему.

## Приём

Упаковка в новый массив стоит аллокации на каждый пакет. Если держать один рабочий буфер, писать в него каждый пакет и отдавать *окно* на него, аллокации исчезают. Это `packShared`:

```ts
const bytes = Packet.packShared(value); // окно на внутренний буфер кодека
```

Для однопоточного JavaScript это верно, **пока байты использованы до следующего вызова**. И вся история в этом «пока».

## Ловушка: `write()` вернулся, а байты не ушли

```ts
socket.write(Packet.packShared(a));
socket.write(Packet.packShared(b)); // перезаписывает байты a
```

`socket.write(buf)` возвращается сразу. Если в буфере отправки ОС есть место, байты тут же копируются в него, и всё хорошо. Если места нет (медленный клиент, телефон на плохой связи, занятая вкладка браузера), Node **держит ссылку на ваш буфер** в очереди записи сокета и отправит позже. Сигнал об этом — `write()` вернул `false`: это и есть *backpressure*.

Пока эта запись в очереди, память за вашим буфером менять нельзя. С `packShared` она меняется уже на следующем пакете: все пакеты в очереди теперь указывают на одну и ту же память, где лежит то, что упаковано последним.

На localhost с быстрым читателем этого не видно, поэтому баг переживает тесты и вылезает в проде. То же самое с любым местом, которое ставит буфер в очередь, а не копирует: массив для пакетной отправки, `await` между упаковкой и отправкой, очередь повторов, стрим. Проверяйте, что API делает с вашим буфером.

## Замер

`npm run backpressure` отправляет пачку из 300 000 мелких пакетов клиенту, который 300 мс ничего не читает:

```
packShared  (view, zero alloc)      160218 of 300000 packets ok   CORRUPTED from packet #160218
pack       (fresh copy)             300000 of 300000 packets ok   all intact
packInto + pool (you own it)        300000 of 300000 packets ok   all intact
```

Первые 160 218 пакетов (около 2,4 МБ) влезли в буферы ОС и ушли сразу. Когда те заполнились, каждый следующий пакет встал в очередь по ссылке и пришёл мусором. Точное число зависит от ОС и размеров её буферов, а форма картины нет.

## Три способа упаковки

| Метод | Что получаете | Аллокации | Сколько живут байты |
|---|---|---|---|
| `pack(value)` | новый `Uint8Array` | одна на пакет | всегда, они ваши |
| `packInto(buf, value, offset?)` | число байт, записанных в **ваш** буфер | нет | пока **вы** не трогаете буфер |
| `packShared(value)` | окно на внутренний буфер кодека | нет | до следующего `pack` или `packShared` этого кодека |

Цена на этой машине (Node 22; `npm run bench`):

| | запись 24 байта | снимок 144 байта |
|---|---|---|
| `pack` | 108 нс | 1246 нс |
| `packShared` | 100 нс (−7 %) | 945 нс (−24 %) |
| `packInto` | 77 нс (−29 %) | 909 нс (−27 %) |

Неожиданность в первой строке против второй. На мелких пакетах общий буфер почти ничего не экономит по сравнению с копией, а `packInto` его всё равно обгоняет: платим за копию и аллокацию, а не за «общность». И `packInto` безопасен, потому что буфер ваш и больше никто в него не пишет.

## Что делать

- **По умолчанию `pack()`.** Одна мелкая аллокация и нечего помнить. На данных из `npm run bench` он уже быстрее msgpackr и cbor-x и в 2–4 раза компактнее.
- **Когда аллокации важны (отправка на игровом сервере), берите `packInto` с буферами, которыми владеете.** Упакуйте пакеты кадра друг за другом в один буфер, отдайте сокету один раз и верните в пул только когда сработал callback записи. В `examples/backpressure.mjs` ровно это в 20 строках.
- **`packShared` только когда вы закончили с байтами до следующего вызова**, в том же синхронном участке кода: посчитать хеш, измерить, сжать синхронно. Его результат нельзя отдавать тому, что может его сохранить.

То же правило действует и на входе: `bytes(max, { view: true })` возвращает окно в буфер, из которого вы читали, а сетевые библиотеки часто переиспользуют буфер, который вам отдали. Там по умолчанию тоже копирование.
